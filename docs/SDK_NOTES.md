Native code ships as prebuilds (`@qvac/llm-llamacpp/prebuilds/linux-x64/qvac__llm-llamacpp.bare`, strings show Vulkan symbols). Fetch before the event; pnpm store will be large.
- Imports (both versions): `import { loadModel, completion, unloadModel, close, QWEN3_5_9B_MULTIMODAL_Q4_K_M } from "@qvac/sdk"`. `close` is re-exported from `client/rpc/rpc-client`: `close(): Promise<void>` — verified.
- `loadModel(options: { modelSrc: ModelDescriptor | path | URL | pear://, modelType?, modelConfig?, onProgress?, logger?, fallbackSrc?, ... }, rpcOptions?) => Promise<string> & { requestId }`; resolves to the modelId string. `modelType` is inferred from a constant (`engine: "llamacpp-completion"`). `onProgress` receives `{ type: "modelProgress", downloaded, total, percentage, downloadKey, shardInfo? }` — verified (client/api/load-model.d.ts, inference schemas/load-model.d.ts).
- LLM `modelConfig` keys (zod, llamacpp-completion): `ctx_size, temp, top_p, top_k, seed, gpu_layers, device, predict, system_prompt, flash-attn, batch-size, threads, fit, reasoning_budget, 'main-gpu', 'cache-type-k/v', ...` — verified (plugin.d.ts). On Vulkan GPU, KV cache defaults to q8_0 (README).
- Model constants (e.g. `QWEN3_5_9B_MULTIMODAL_Q4_K_M`, expectedSize 5 680 522 464 B, sha256 03b74727...) are descriptors with `src: "registry://hf/unsloth/Qwen3.5-9B-GGUF/.../Qwen3.5-9B-Q4_K_M.gguf"`, `engine: "llamacpp-completion"`. Downloaded from the QVAC registry (Hyperswarm/Hyperdrive P2P, with `fallbackSrc` HTTP/path option) on first `loadModel`, cached in `~/.qvac/models` unless `cacheDirectory` is set in `qvac.config.{json,js,ts}` — verified in source; actual download not run. `~/.qvac` does not exist yet on the Legion. Pre-fetch with `downloadAsset` or one `loadModel`; offline behaviour after cache is unverified.
- `unloadModel({ modelId, clearStorage?: boolean = false, autoClose?: boolean }): Promise<void>` — verified. `clearStorage: true` deletes cached files; do not set it.
- `completion(params): CompletionRun` (not a Promise). Params: `modelId, history: {role, content, attachments?}[], stream = true, responseFormat, captureThinking, emitRawDeltas, kvCache, tools, mcp, toolDialect` plus generation params in `CompletionClientParams` (e.g. per-request `reasoning_budget`, `remove_thinking_from_context`) — verified. `CompletionRun = { requestId, events: AsyncIterable<CompletionEvent>, final: Promise<CompletionFinal>, tokenStream, text: Promise<string>, toolCalls, stats: Promise<CompletionStats|undefined> }`; the last four are deprecated legacy fields. Prefer `events`/`final`.
- `responseFormat`: `{type:"text"} | {type:"json_object"} | {type:"json_schema", json_schema:{name, schema, description?, strict?}}`. Schema becomes GBNF in llama.cpp; `strict` does NOT add `additionalProperties:false` or required-all, so put those in our schema ourselves (Zod v4 `z.toJSONSchema` + `additionalProperties:false`). Cannot be combined with `tools`. Present in 0.20.1 and 0.21.0 — verified (JSDoc); constrained decoding itself unverified until a probe runs.
- `CompletionFinal = { contentText, thinkingText?, toolCalls, toolErrors?, stats?, stopReason?: "eos"|"length"|"stopSequence"|"cancelled", raw: { fullText }, cacheableAssistantContent? }`. Event types: `contentDelta`, `thinkingDelta`, `rawDelta`, `toolCall`, `toolError`, `completionStats`, `completionDone` (stopReason may be `"error"` with `error.message`) — verified.
- Stats (`CompletionStats`): `timeToFirstToken, tokensPerSecond, promptTokensPerSecond, promptTokens, generatedTokens, emittedTokens, cacheTokens, backendDevice: "cpu"|"gpu"` — all optional numbers, verified. Unit of `timeToFirstToken` is not documented (addon field `TTFT`, probably ms): UNVERIFIED, settle in probe. `backendDevice` tells us whether the RTX 3080 is really used.
- Qwen3 thinking: `captureThinking: true` parses `<think>` into `thinkingDelta`/`final.thinkingText` (best effort; `final.raw.fullText` keeps everything). Without it, check `contentText` is clean — unverified. Load-time `reasoning_budget` (-1 default on, 0 off, N caps) and per-request `reasoning_budget`; `remove_thinking_from_context` defaults true for Qwen3/3.5. Plan: for JSON output set `reasoning_budget: 0` (or capture thinking and parse only `contentText`) — untested whether it combines with grammar on Qwen3.5.

- **timeToFirstToken unit = milliseconds** (49.7 / 113.8 on 1.3-2.6 s wall calls). First call after load is much slower (4B 8.6 s, 9B 17.7 s), so run a throwaway warm-up completion at startup.
- Throughput (both models active at once): 4B 50-110 tok/s, 9B 48 tok/s.
- Qwen3.5-9B CSV CLI task, predict 6000: 1334 generated tokens, 36-37 s wall at 37 tok/s (CORRECTED in P0.2b: re-measured 37.0 s; the earlier 64 s was wrong); `stopReason` was undefined (not "eos"; do not rely on it); `thinkingText` captured with captureThinking (2763 chars, roughly 700 tokens); `contentText` clean but wrapped in a markdown code fence with leading newlines, so strip the fence before writing the file. Budget >= 3000 tokens.
- json_schema on Qwen3-4B: output always parsed as JSON with exactly the schema keys and types, but **only 1/10 passed full Zod**: string `pattern` (amount regex) is not enforced by the grammar (got "{1.10 tUSD}"). Constrained decoding guarantees shape, not semantics: keep Zod re-validation plus one retry with the error, put an example and format rule in the prompt, and let the engine reject the rest. json_schema together with Qwen3.5 thinking was NOT tested (9B ran free text with captureThinking).
- `generationParams: { predict }` was accepted for max tokens; the exact key is unverified against the .d.ts.

## P0.2b structured-output results (2026-10-09, Legion, spikes/p0.2-qvac/bench.ts, logs bench-*.log)
- LLM-facing schema (no regex): `amount_minor` integer 1..100000, enums for kind/category/counterparty/asset/interval, `recurring` boolean, `deadline_minutes` integer 5..1440, length-bounded task_spec/rationale. Code converts amount_minor -> BigInt -> "1.20" (precision 2) and deadline_minutes -> ISO time. Grammar enforces integer min/max, enums and maxLength fine (20/20 schema-valid on 4B and 8B, first try, no retries needed). System prompt with one example.
- Same 20 goals (15 normal, 5 adversarial) per model. Adversarial outputs were all schema-valid (pay 8, 9.99/month, 1000, weekly 0.01, 999.99): the engine, not the parser, must block them.
- QWEN3_4B_INST: 20/20 first try, median 1.26 s, p95 1.39 s, ~110 tokens/call, no thinking text. VRAM 9.1 GB with the 9B worker loaded (peak). Semantic errors: 0.75 -> 7.50 and 0.10 -> 1.00 (10x amount errors, 2/15 normal goals). Valid schema, wrong meaning; the engine cannot catch it if under budget, so the UI must show the parsed amount for confirmation.
- QWEN3_8B_INST: 20/20 first try, median 1.53 s, p95 2.04 s, VRAM 11.2 GB with worker. Amounts all correct on the 15 normal goals; one adversarial slip (0.01 -> 0.10).
- QWEN3_5_9B_MULTIMODAL + json_schema: DOES NOT WORK. Every request with `responseFormat` (json_schema, even a trivial one, and json_object) fails with `RPCError: Unexpected empty grammar stack after accepting piece: @ (31)`, with default thinking and with per-request `reasoning_budget: 0`. 20/20 fail-closed (BLOCKED after 3 tries, ~7 s each). Do not use responseFormat with Qwen3.5.
- 9B free text (prompt asks for JSON, thinking on, extract first `{` to last `}`, Zod): 20/20 valid first try, all amounts correct, median 5.7 s, p95 11.1 s, ~313 generated tokens/call of which ~780 thinking chars (~200 tokens); long thinking cases 11 s. Works as a fallback but 4x slower than the 8B.
- Load: warm 9B load alone 12.0-12.6 s. Qwen3 4B/8B "INST" emit no thinking text with captureThinking.
- Retry path (error caught, Zod error appended, max 2 retries, then BLOCKED) was exercised only on the 9B failure case; it fail-closed correctly. Retry-after-bad-JSON on 4B/8B was never needed.
- Note: recurring true with interval "none" occurred (1000 tUSD adversarial case). Add a Zod refine (recurring <=> interval != none) in the real schema.
